# v1.5.0 — human verification before READY

Released locally September 4, 2026, from v1.4.0 commit `baf9e34`.

v1.4.0 over-trusted automated extraction. A fourth audit reproduced incorrect
affirmative proposals from negated diagnoses and strength, reflex qualifiers
borrowed from pain, resolved findings and unrelated therapy. Some negation
behavior contradicted the extraction contract as written. This release changes
what the engine may assert; it does not repair those language patterns.

## Behavior and compatibility

- Every requirement result exposes a proposed `fact_value`, verification state,
  reviewer/time and proposal fingerprint. Default state is `UNVERIFIED`.
- New frozen status `PENDING_VERIFICATION` replaces automated all-MET READY.
  It always has `submission_readiness=false`. READY requires all operators MET
  and every requirement fact HUMAN_VERIFIED. NOT_READY, CANNOT_DETERMINE and
  NEEDS_REVIEW retain their precedence and meaning.
- Attestations bind to the normalized request, runtime rule bundle, requirement,
  value, operator result and spans. Note/scope/rule changes require fresh review;
  unknown keys and stale fingerprints are rejected. Verification cannot edit
  values or override failed, missing or ambiguous requirements.
- Streamlit has per-fact verification controls. FastAPI accepts the same
  `fact_verifications` mapping. CLI accepts `--request-file` and
  `--verifications-file`. Structured exports retain reviewer/time metadata.
- Letters preserve PENDING_VERIFICATION and do not assert readiness for an
  unverified all-MET case. Existing policy/rulebook submission gates still apply
  after full human verification.

Consumers must handle the new status and additive result/request fields.
There is no automatic migration of old READY results into human attestations.
Application version is 1.5.0; the policy rulebook remains version 1.0 because
no payer criteria or policy releases changed.

## Narrow integrity fixes

- Unicode: regex offsets in lowercased text are mapped back to original-note
  character offsets; captured span text is copied from the original slice.
  Span coercion no longer strips that text. This guarantees source location,
  not semantic support, correct attribution or complete context.
- Cache: long-lived services reread runtime rules, provenance and policy sources.
  A completed promotion takes effect without restarting FastAPI. A detected
  bundle change between evaluation start/end fails the request for retry.
- Monitoring: an unknown or misspelled frequency yields UNKNOWN freshness and
  requires review; it cannot silently disable freshness enforcement.

## Validation

- Full suite: **359 passed**, including all **287 existing cases** (with
  intentional v1.5 expectation updates) and **72 new cases**; no skips or xfails.
- Ruff lint, formatting and whitespace checks passed.
- Executable contract class covers all seven numbered guarantees and 36 exact
  examples, beginning with the negated-diagnosis false proposal and its blocked
  READY outcome. Unicode source slices are also checked across the full corpus.
- Cross-surface tests compare identical unverified and human-verified requests
  across Streamlit, FastAPI and CLI, including status, submission readiness and
  attestation metadata.
- Regression tests cover completed rule promotion in a running API, rejection
  of prior attestations, a mid-evaluation bundle change, and misspelled cadence
  with matching runtime/active source files so the freshness gate is isolated.
- Live localhost API smoke returned PENDING_VERIFICATION unverified and READY
  with synthetic attestations. Streamlit health and root-page checks passed;
  application interaction was exercised through AppTest.
- Golden evaluation snapshots include both unverified and explicitly verified
  fixtures. Generated artifacts reproduce without changes.
- Labeled synthetic corpus: **52/52 exact statuses**; 7 PENDING_VERIFICATION,
  3 NOT_READY, 30 CANNOT_DETERMINE, 12 NEEDS_REVIEW. Zero automated READY is a
  structural gate property, not evidence of extraction accuracy.

## What remains unresolved

Negation, temporality and attribution extraction errors remain intentionally
unfixed. The old general affirmative-negation promise cannot be reconciled
with the unchanged extractor; it has been replaced by candid proposal semantics
and executable examples. No ontology, LLM, RAG or NLP dependency was added.

Human identities and times are caller-supplied; this local prototype does not
authenticate reviewers, prove review occurred, or provide a tamper-resistant
attestation ledger. Incorrect or fabricated attestations can still permit false
READY. Runtime file reads are not a transactional deployment mechanism.

The borrowed sleep-study date was already contained at the submission boundary:
v1.4.0 could return READY documentation status but submission_readiness=false
under demo policy trust, as the README permitted. v1.5.0 additionally requires
verification; the date-association error itself remains.
