# v2.0.0 — structured reviewer correction of requirement facts

Released October 5, 2026, from v1.6.1 commit `f2655e2`, with the correction
implementation reviewed in [PR #6](https://github.com/NickLeko/PriorAuthorizationCopilot/pull/6).

v1.6.1 required human verification but could not replace an incorrect extracted
proposal or supply a requirement fact that extraction missed. v2 makes that gate
actionable through typed reviewer corrections over immutable original proposals.

## Behavior and compatibility

- Ordered `SET_VALUE`, `SET_MISSING`, `SET_NEEDS_REVIEW`, and `RESTORE_ORIGINAL`
  corrections materialize effective facts without changing the retained original
  proposal. SET_VALUE corrections are source-located in the submitted note.
- Fact contracts drive entry, representation, units, meanings, and
  reviewer-enterable values. Streamlit exposes contract-driven controls; API and
  CLI accept the same structured correction payloads.
- Every correction changes the fact-set fingerprint and invalidates all prior
  attestations. Effective facts must be reviewed and attested again. READY still
  requires every requirement to pass and every fact to be HUMAN_VERIFIED;
  policy and rulebook trust separately control submission readiness.
- READY keeps its existing status. `uses_reviewer_corrections` and
  `corrected_requirement_keys` annotate evaluations that depend on a correction
  history, including one ending in RESTORE_ORIGINAL.
- Letters disclose reviewer-supplied requirement facts, effective values, source
  quotations, and self-reported editor/verifier identities. Structured exports
  retain original proposals and the full ordered correction list.
- New records use schema `2.0.0`. Version-aware archive reads retain historical
  records without migrating their proposals into corrected or verified facts.
  Corrected decisions are viewable, not replayable.

Consumers must handle the correction envelope and annotations. Release and
record schema versions remain independently versioned. The canonical
[correction limits](../safety_and_scope.md#correction-limits) apply to this
release; this document does not duplicate them.

## Narrow integrity fixes

- Streamlit checks cached-result, attestation, and letter context on every rerun.
  Governance or bundle changes and failed re-verification clear stale outputs
  and explain why.
- Letter generation revalidates the complete evaluation envelope before deriving
  inputs, rejecting inconsistent materialization, annotations, or evidence.
- Streamlit preserves numeric entry until strict contract validation, rejecting
  fractional weeks without truncation. Overlength audit comments are rejected
  rather than shortened by the widget.
- Archive validation recomputes metrics from validated results and enforces
  agreement across policy-trust copies, including the supported procedure.
- API validation rejects non-finite and overflow JSON numbers with structured
  422 responses before validation-error serialization.
- SET_VALUE span count and size caps are enforced at correction, archive, and
  letter boundaries.

The Streamlit stale-output issue and missing archive metric/trust-copy checks
also exist in v1.6.x and are fixed here. v1.6.x tags are unchanged.

## Validation

- Full suite on main: **760 passed**, including **29 audit-fix regressions**;
  no failures, skips, or xfails.
- PR #6 CI passed Ruff, pytest, historical artifact/golden generation, and the
  generated-file consistency check.
- Labeled synthetic corpus: **52/52 exact statuses**, with no status changes;
  7 PENDING_VERIFICATION, 3 NOT_READY, 30 CANNOT_DETERMINE, 12 NEEDS_REVIEW.
- Corpus conformance: **163 captured values**, 446 missing states, 15 review
  states across 52 cases; **zero nonconforming captured values**.
- Regression coverage includes stale UI contexts, invalid letter envelopes,
  strict Streamlit entry, archive metadata forgeries, non-finite API inputs,
  and evidence-span count/size boundaries.

## What remains unresolved

Extraction, operators, policies, and the 52-case corpus are unchanged. Existing
negation, temporality, and attribution extraction errors remain; this release
does not claim improved extraction accuracy. Correction limitations remain in
the canonical section linked above.
